## 2. What it extends (no duplicate systems)
- `EXISTING` `StationDevice` (durable device id, branch, zone), `BranchMasterDesignation`, one-time `BranchActivationCode` + `/api/stations/activate` (**the door for unattended stations stays exactly as it is**).
- `EXISTING` `WorkspaceMember(role)`, `MemberScope` (presets + `allLocations`, F2a shadow), `UserBranchAssignment`, capabilities (blueprint §3) and composite scopes (D21).
- `EXISTING` `WorkspaceEntitlement` (`maxBranches`, `maxDevices`, `maxUsers`, `maxPlaylists`) and `lib/entitlement-limits.ts` (enforcement behind `SYNCBIZ_ENFORCE_LIMITS=1`).
- `EXISTING` the signed WS token (`designatedMasterByBranch` claims) minted by the app — **the one choke point** this design uses.

## 3. New data (additive only)
1. `DeviceEnrollment` (`NEW`): id, workspaceId, `durableDeviceId`, `status` = `pending | approved | rejected | revoked | expired`, `requestedRole` / `approvedRole` = `PLAYER | REMOTE`, requestedBy (user), device label, platform, app version, IP + country, requested branch (optional), approved scope (branches / zones), decidedBy, decidedAt, note, `expiresAt`, lastSeenAt. One live row per (workspace, durableDeviceId).
2. `WorkspaceRole` (`NEW`) — the Discord-like part: id, workspaceId, name, colour, `capabilities[]`, `isPreset`. Presets are seeded from blueprint §3 (Owner, HQ Control, Regional Manager, Branch Manager, View Only) and can be copied / edited; custom roles are free. `MemberScope.roleId` (`EXTEND`, nullable) points at it, so a role is assigned **with a scope** (organization / brand / region / location(s) / zone — D21).
3. `WorkspaceEntitlement.maxPlayers` (`EXTEND`, additive, default = `maxBranches`): the allocation for **players**. `maxDevices` is left untouched (its V1 comment counts control computers and phones too, which contradicts E4); it is retired later, not repurposed.
4. `Workspace.enrollmentSettings` (`EXTEND`, JSON): `{ enabled: false, requestTtlDays: 7 }`. **`enabled=false` = today's behaviour for that workspace, exactly.**

## 4. New capabilities (added to blueprint §3)
`devices.view` · `devices.approve` (+ choose role and scope) · `devices.revoke` · `allocation.manage` (change seats, where the entitlement allows) · `remote.connect` (be approved as a Remote for a scope) · `display.configure` (design + opening hours of a branch screen — ties to Track B) · `roles.manage`.
**Rules (blueprint-§3 style, server-enforced, never UI-only):** nobody can grant a capability or scope they do not hold; a branch role can never approve outside its scope; only OWNER / ADMIN can approve a **Player** into a zone that has no designated MASTER or designate one (`master.designate`, D1 — unchanged); every decision goes to `AuditLog`.

## 5. The flows
**5.1 Device status call (`NEW`)** — `POST /api/devices/enrollment/status` `{ durableDeviceId, platform, appVersion, label }` → `approved { role, branches/zones }` · `pending { requestedAt, expiresAt }` · `unknown` · `rejected` · `revoked` · `expired`. Same call for computers, phones and stations. Stations that already hold a designation answer `approved` without any request (the existing `GET /api/stations/activate?deviceId=` result is the input).

**5.2 Request** — an `unknown` / `expired` device shows one calm screen: *"This computer is not part of the account yet — ask the manager"* with **Player / Remote**, the branch (only branches the signed-in user may see) and a note → `POST /api/devices/enrollment/request`. The screen then shows "waiting for approval" and polls with back-off (no polling flood). **A not-yet-approved device gets no WS token** and cannot play or control.

**5.3 Approval (Control Room, `NEW`)** — "Waiting for approval (N)" list: device name, platform, requested role, who asked, when, where from. Approve opens a small dialog: **role** (Player / Remote), **branch / zone**, optional note; shows the allocation meter *"Players 12 of 20"*; a Player over the limit is refused with a clear message (enforced when `SYNCBIZ_ENFORCE_LIMITS=1`). Reject / revoke any time. Branch owners see only their branch's requests. **If the zone already has a designated player, the dialog offers exactly two explicit choices — "standby" (a second Player that stays CONTROL until an admin promotes it) or "replace the current player" (needs `master.designate`, asks for a confirmation that names the current player, is written to the audit log, and demotes the old one); never a silent second player.**

**5.4 What each role does after approval**
- **Remote** (computer or phone): connects as CONTROL for its approved scope only; **the server forces CONTROL — a Remote can never become MASTER**, not on reconnect, not when the player is offline (matches the permanent-MASTER invariant).
- **Player**: bound to its zone (`StationDevice`). The designated MASTER of a zone is still chosen only by an explicit, audited admin action (`master.designate`); a second Player in a zone is a **standby** (CONTROL until an admin promotes it — no automatic failover, unchanged).
- Phones are **Remote only** (the server already refuses a mobile MASTER); an Android TV streamer can be a Player.

**5.5 New branch** — a Player request that names a branch that does not exist is a *"new branch"* request: the approver creates / links the branch, and it counts against `maxBranches`.

**5.6 Notifications (E6, E7)** — email to the approver(s) of that scope (with an approve link that opens the Control Room, never a one-click approve from the mail), a phone notification when the manager has the app (Phase 5), and in the Control Room a "Waiting for approval (N)" badge plus a player icon with a status dot on every branch. **Version 1 = the Control Room badge and icons only.** Email comes next, through the existing Resend integration (`lib/email/resend-transactional.ts`) — **but** it has only a password-reset function (an enrollment mail is a new function), `RESEND_FROM` is optional and defaults to `onboarding@resend.dev`, which Resend delivers only to the Resend account's own address, so mail to managers needs a **verified sending domain** + `RESEND_FROM` + `RESEND_API_KEY` (**not yet verified on PROD / TEST**; to be checked from the dev-PC session); phone push only with the phone app (Phase 5).

## 6. Where it is enforced — THREE points, not one (corrected by the Phase 0 audit, see §11)
1. **Token mint.** `GET /api/auth/ws-token` (browser, renderer, phone, controller) and the two desktop routes (`/api/auth/desktop/token`, `/token-from-session`). When the workspace has `enabled=true` they must know **which device** is asking and refuse a token to a device that is not `approved`; the signed claims then carry `enrollment: { role, scope }`. The desktop routes must run the check **before** they register the `StationDevice` (today registration happens first, so a row's existence cannot mean "approved").
2. **WS `REGISTER`** (`server/index.ts`). In an enrolled workspace the **role comes from the claim, not from the client message** (today a client may ask for `owner_global` / `controller` / `device`), and a Remote is forced to CONTROL. This **is new WS logic** — own gate, own tests, and a Lenovo-class regression run.
3. **Revocation.** Issued tokens live 60 s (browser) or 7–30 days (desktop) and a socket is checked once at connect. Revoking a device must also **push a disconnect** to the WS server (the server already has secret-protected `/internal/*` endpoints) and the token must carry the enrollment flag so an old token cannot outlive a revoke past its expiry.
**Legacy tokens (corrected after review round 2 — the earlier line "absent claim = legacy, always" let an old 7–30-day desktop token bypass enrollment in an enabled account).** The WS server is DB-less, so it needs a small **per-workspace enrollment state pushed by the app through the secret `/internal/*` channel** (the way designations are synced today): `{ enabled, grandfathered stationDeviceIds }`, pushed when the flag is switched on and again whenever the WS server restarts / the app reconnects. Rules: a workspace **not in that state** = legacy exactly as today; in an **enabled** workspace a token **without** an `enrollment` claim is accepted **only if** its `stationDeviceId` is on the grandfathered list (the running stations keep working for the life of their token, offline included), otherwise it is refused. Browser / renderer tokens live 60 s and are always re-minted, so they always carry the claim. **Open point (restart window):** between a WS-server restart and the next push, tokens that carry a `stationDeviceId` are accepted (a running station must not lose remote control); browser tokens cannot be judged and follow today's behaviour for that short window.

**Iron rules for the refusal path (verified in code):**
- **A refusal is never sent to a station as `SET_DEVICE_MODE` CONTROL or `designated:false`.** In desktop MAIN that signal clears the designation cache and **stops the station's music** (`desktop/src/device-websocket-client/device-ws-manager.ts:253-283`, `applyDesignationSignal`). A refusal uses a **dedicated close / error code** that MAIN treats as "keep everything as it is" — Phase 4b must first check how MAIN handles unknown close codes; if MAIN needs a change, Phase 4b is also **DESKTOP MAIN** (new installer for the Lenovo test).
- **A refusal at `token-from-session` must be terminal.** Only HTTP 409 (conflict) is terminal today; any other non-OK answer, including 403, is treated as transient and **retried forever** (`lib/use-desktop-activation.ts:52-53`, `lib/desktop-activation-core.ts`). Enrollment refusals use 409 or a new terminal status handled there.

## 9. Acceptance tests (written before Phase 4)
**Offline (runtime acceptance, Lenovo-class):** an approved Player with the network cut keeps the current track and does not advance the queue; its token expires while offline and nothing stops or restarts; the **computer is rebooted with no internet and the approved Player starts its local playback** (constitution §15); on reconnect it re-mints a token carrying the enrollment claim; a revoke made while it was offline takes effect when it reconnects, not before. · Unknown device → request → pending → approve → connects with the right role · reject / revoke / expiry (7 days) · Player over the allocation refused · Remote never becomes MASTER (player offline, reconnect, order of startup) · branch owner cannot see or approve another branch · nobody grants what they do not hold · flag off = identical behaviour to today (the Lenovo regression list in the baseline) · two people in one account: the second computer asks for approval instead of silently being a remote.

## 10. Risks / open items
- **Device id is not a secret** (a copied id could be replayed): fine for Phase 4 behind a signed-in session; Phase 5 adds the revocable credential.
- **Scope in the WS token:** broad scopes must carry the expression, not an expanded id list (blueprint D21) — decided in Phase 0.
- **Existing devices when the flag turns on:** all already-registered `StationDevice` rows are auto-approved ("grandfathered") so nothing goes dark; an admin reviews the list once.
- Email: a verified sending domain and the notification mail function (see §5.6); push depends on the phone app (Phase 5).
- **The Android native streamer does not exist yet** (owner, 2026-10-27: "there is no Android for now — we will sit on it later"). The `/streamer` web page and the Android-shell code paths in the repo are for it; its token source is to be designed together with it, before Phase 4b is declared complete for Android.
- Naming for the UI (Hebrew): נגן / שלט רחוק, "ממתין לאישור", "הקצאת נגנים" — to confirm with the owner when Phase 3 starts.
